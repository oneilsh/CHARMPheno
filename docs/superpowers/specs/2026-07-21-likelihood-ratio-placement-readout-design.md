# Likelihood-ratio placement readout + per-code viewer + NPMI — design

**Status:** approved (brainstorm 2026-07-21). Exploratory research build; no
production target. Post-hoc on an already-fitted gated-LDA case-finding run;
**no re-fit required.**

## Motivation

The 0061 topic dump showed that the gated node topics DID learn coherent,
disease-specific signatures (e.g. SLE topic 53 = lupus erythematosus / discoid
lupus / alopecia / dry eyes; scleroderma topic 67 = Raynaud's / systemic
sclerosis / ILD; MG topic 149 = diplopia 0.33 / ptosis 0.19). But they are
**mass-starved**: node topics carry Σλ ≈ 10²–10³ vs background topics' 10⁵–10⁶,
so node E[β] ≈ 0.0008 → 0.0000. The placement readout `P[u]` is θ-mass — a
simplex competition the starved node topics cannot win, so known cases place
≈0 weight on their disease phenotype, and the FDR readout found zero
discoveries.

θ-mass answers "what fraction of this record was generated by the disease
topic?" — record composition, dominated by base rates. The detection question
is "does this record carry the disease's signature more than a typical
patient's?" — a classification question whose natural statistic is a
likelihood ratio built from the learned β. This readout reuses the topic model
as a feature learner and reads it as a per-node Naive-Bayes detector, bypassing
the θ simplex entirely.

## The likelihood-ratio readout

For patient i and node u:

  s(i, u) = Σ_w count(i, w) · log[ P(w │ node u) / P(w │ background) ]

- **P(w │ node u):** the node block's λ rows summed then row-normalized (this is
  the Σλ-weighting — floor-junk topics in the block contribute ~nothing).
- **P(w │ background):** the corpus base rate — code frequency from the BOW
  (robust, no dependence on background-topic estimation).
- **Shrinkage (the noise control):**
  P(w │ node u) = ( λ(u,w) + α · P_bg(w) ) / ( Σλ(u) + α ).
  α is a pseudo-count of background belief; large α pulls mass-starved nodes
  toward the base rate so under-evidenced codes contribute ≈0, and sends codes
  the node never saw to a neutral log-ratio ≈ 0 (rather than −∞). Two nuances:
  (1) in log-space, genuinely distinctive codes survive strong shrinkage (their
  ratio to a near-zero base rate stays large); (2) α>0 also gracefully handles
  out-of-node-vocab codes.

Why it beats θ-mass: no simplex competition (each node scored independently, so
a starved-but-coherent node can still fire); the log-ratio is idf for free
(common codes → ratio ≈0/negative, cannot drown the signal); per-node and
independent, so multimorbidity is native (a patient can score high on several
nodes at once).

### α is a swept diagnostic, not a fixed default

The script reports **LR-AUC as a function of α**, always including **α = 0**
(pure MLE — maximum sensitivity to rare codes and to noise; needs a small ε
floor to avoid log(0) on unseen codes). Rising α trades sensitivity for
robustness. No hardcoded default is chosen in this build; the α-curve IS the
experiment (does shrinkage help or discount rare diseases too much?). **Default
α grid:** `{0, 0.1, 1, 10} × median(node Σλ)` — auto-scaling to the fit's
starvation level (0 = none; ~median = balanced; 10× = strong), configurable via
a `--alpha-grid` flag. ε (the log-floor at α=0) is a fixed small constant
(e.g. 1e-9, distinct from α, pinned in the plan) applied to any P(w│u)=0 so the
contribution is a bounded negative rather than −inf.

### Score variants reported

- **raw** Σ over codes, and **length-normalized** (per-token mean), since long
  records accumulate more terms — the FDR machinery (if wired later) can ride
  on whichever separates.
- **count handling:** raw `count(i,w)` by default; `log(1+count)` saturation
  available as a knob so one heavily-recorded condition cannot dominate.

## Components

### 1. Engine (`spark_vi`, id-agnostic — arrays + DagLayout, no concept-ids)

- `lr_placement_scores(bow, lam, lay, *, alpha, background, epsilon, count_mode,
  length_normalize) -> np.ndarray [n_docs x n_nodes]` — the shrunk log-LR score
  per (doc, node). `bow` is a docs×V count matrix (or sparse); `lam` is the K×V
  counts from the npz; `background` is the base-rate vector (or "corpus" to
  derive it from `bow`).
- `lr_decompose(bow_row, lam, lay, u, *, alpha, ...) -> list[(w, count,
  contribution)]` — the SAME sum, itemized per code (the viewer). Sums to
  `lr_placement_scores(...)[i, u]` by construction (a test asserts this).
- Reuse `spark_vi.eval.topic.compute_npmi_coherence(beta, holdout_bow,
  top_n=...)` for per-topic coherence (β = row-normalized λ).

### 2. Domain analysis script (`charmpheno`/`analysis`, the enclave edge)

A standalone in-enclave script the user drives. It:

- **Loads** from a run dir: `dag_placement_result.npz` (λ, α_dirichlet — the
  fit's own α, unrelated to the shrinkage α) and the run manifest. Locates the
  cached `CaseFindingBundle` (test BOW + frontier + `vocab_map` + `parent_int`
  + `name_by_id`) by recomputing the corpus cache key from the manifest config;
  accepts an explicit `--bundle-path` override and warns on a source-hash
  mismatch (the fragility of no-re-fit — the corpus/assembly source may have
  changed since the fit).
- **(a) Fork-settler:** computes LR-AUC(α) (case-vs-background, foreground =
  non-empty frontier) over an α grid including 0, printed alongside the
  existing θ-mass detection AUC. LR-AUC ≫ θ-AUC → signal present but buried
  (detection fixable); LR-AUC ≈ θ-AUC → signal genuinely absent (information
  wall → richer features).
- **(b) Per-code viewer:** for user-selected known cases, renders
  `lr_decompose` with **concept names** (via `name_by_id`/`vocab_map`) — which
  codes pushed toward the disease node (+) and which toward background (−).
- **(c) NPMI table:** per-topic coherence, ranking the node topics so the
  coherent ones (53, 67, 48, 149, 59…) sort above the floor-junk.

Rendering to concept names is the domain edge and lives here, not in the engine.

## Data flow / loading (no re-fit)

`dag_placement_result.npz` already persists `lambda` (K×V) and `alpha`. The
cached bundle already carries `vocab_map`, `parent_int`, `name_by_id`, and the
test `bow`/`frontier`. So every input exists on disk after a run; the script is
pure post-hoc read. λ column order = `vocab_map` order (both indexed by the
engine vocab id).

## Egress / safety

The script runs **in-enclave**; per-patient decompositions (row-level) are for
the user's eyes and never leave. Only aggregates — LR-AUC(α), the θ-vs-LR
comparison, NPMI per topic — are candidates for export, under the same
aggregate-only rule as the existing covariate/topic exports. The script writes
row-level views to the run dir (stays in the enclave); aggregate summaries to a
separate file.

## Caveats (documented in output)

- **Screen, not diagnosis.** The background contains thousands of unmodeled
  diseases; the LR ignores those without a node (log-ratio ≈0), so detection
  survives, but near-neighbor *mimics* (e.g. RA scoring on the SLE node) are the
  specificity ceiling. A modest LR-AUC may mean mimic-confusability, not absent
  signal — a third fork outcome, and the argument for the fuller ontology DAG.
- **Node β is noisy** (few frontier-{u} docs); the α-sweep is how we probe the
  bias/variance tradeoff rather than assume it.
- **In-sample** (the null/base rate is the same corpus scored).

## Out of scope

- Wiring the FDR machinery onto the LR score — a deliberate follow-on, only if
  the α-sweep shows LR-AUC ≫ θ-AUC (signal present but buried).
- The exportable-null artifact (that is the FDR sub-project's SP2).
- Any model/gate/window/anchor change — this is post-hoc on the fitted λ.
- A driver-integrated (inline) variant — kept standalone for interactive
  pixel-peeping; the fit already persists everything needed.

## Validation

- Engine unit tests (pure numpy, no Spark): a planted distinctive-code case
  scores high on its node and a common-code-only patient scores low (LR
  separates where θ-mass would not); shrinkage monotonicity (rising α pulls
  starved-node scores toward 0; a once-seen coincidental code's contribution
  shrinks faster than a many-times-seen signature code's); `lr_decompose` sums
  exactly to `lr_placement_scores`; α=0 ε-floor prevents −inf and is finite;
  length-normalization and count-saturation knobs behave.
- The loader / name-rendering / bundle-location is exercised in-enclave on the
  real 0061/0062 runs (cluster-covered, like the other BQ/driver paths), not
  unit-tested here.
- The real read: LR-AUC(α) vs θ-mass-AUC on 0061/0062 — does the coherent-but-
  starved node signature separate cases from background once read through the
  likelihood lens?
